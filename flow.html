The flow

How a requirement becomes a component that can be built without asking back — and which artefact carries which part of that. Marked throughout: what runs today, and what does not exist yet.

← Components
  1. 1

    Specification

    exists — their system

    States what has to be possible. Deliberately does not state how it is presented — a spec that prescribes the control is reaching into design.

    Consequence: the behaviour is undefined at this point, and that is correct. It only becomes a problem when nothing downstream defines it either.

  2. 2

    Design in Figma

    exists — their system

    States what it looks like, and with variants what it looks like either side of a threshold. Components come from the component library, colour from the three-tier tokens.

    The behaviour goes into the component description — three to five sentences, at the component, without leaving the tool. It travels with the component and is readable through the API.

    Figma holds states, not rules. Two variants show what happens either side of a threshold; they cannot say where the threshold sits.

  3. 3

    Prose becomes a rule

    today by hand · skill planned

    The description, the spec and the cross-cutting rules are turned into one rule file: what applies, why, the edge cases, who decided it — plus the executable logic.

    And a list of what none of the sources answered. Those are asked, never invented. A plausible-looking answer nobody actually chose is worse than an open question, because it looks like a decision.

    The planned skill does not standardise the rules — their content differs every time. It standardises the questions: every threshold rule gets asked what happens at exactly N, every space conflict gets asked what may not be sacrificed. Same questions, different answers.

  4. 4

    waitingroom

    built — this is it

    The rule becomes executable. A control panel drives it past its own thresholds, so what is on screen is the rule working rather than one result somebody picked.

    Prototype, rule text and code snippet all come from the same file. Change the threshold and all three change together — there is no second place to keep in sync.

    Explicitly not production code. That was the failure mode last time: something arrived looking like a delivery and was measured against production standards. A holding room is not a treatment room.

  5. 5

    Engineering checks it

    next step

    “Could you build this from it, without asking the designer?”

    Every “no, I'd still need…” is a line missing from the rule. That is the measurement — the prototype is only the means.

  6. 6

    Answers flow back

    built

    Answers become edge cases. Changes become entries in the change trail, with a reason — not silent edits that make it look as though it had always been that way.

    Two of the three rules here already carry a second entry. Both changes were found by working the prototype, not by reading anything.

  7. 7

    Implementation

    their system

    Built in the real stack, from a rule with no gaps left in it. The code snippet is framework-neutral on purpose — the decision, not the rendering, so it still holds when the component library moves a major version.

Which artefact carries what

Each of these exists because something would otherwise have to be decided again every time. That, not typing speed, is where throughput comes from.

ArtefactCarriesStatus
rules/*.js
one file per rule
 The single source. Prototype, rule text and snippet all derive from it. built
Figma component description
at the component
 The designer's intent, in a few sentences, without a change of tool. in use
design.md
one level above the rules
 What holds everywhere and must not be repeated per component: person names, selection controls, missing data, “other needs a free text”. Plus the rule types and their question lists. planned
rules skill
prose → rule
 Same questions every time, same output format, same shape. Translates — never authors. What the sources do not say becomes an open question. planned
check script
runs on every change
 All fields present, change trail non-empty, open questions not empty, and no parameter value spelled out as a literal in prose — the drift that already happened once here. planned
docs/*.md
generated
 The linkable, archivable form of a rule. Output, never source. built

The order matters: the check script first, because it makes consistency measurable; design.md from what the script cannot check; the skill last, because it needs both as its yardstick. Writing the skill first would produce exactly the uneven quality it is meant to prevent.

Where the throughput comes from

  • Fewer questions back. Every edge case settled in advance is a message not sent, and a wait not had.
  • Fewer full rounds. A colour change is a token change. Where component and design point at the same token, nothing needs rebuilding and nobody needs to hand anything over.
  • Fewer decisions. Once “from five options on, a select” is settled, component number forty inherits it. This is the one that compounds — and the reason a design.md full of decisions is worth more than one full of style guidance.

None of this makes anyone build faster. It removes the waiting in between.

Everything on this page that is marked planned does not exist yet. The three components under Components do — including two rules that changed within a day because working the prototype exposed something reading it had not.
