The workflow

How a requirement becomes a component that can be built without asking back. Marked throughout: what runs today, what does not exist yet.

  1. 1

    Specification

    exists — their system

    States what is needed — user stories and acceptance criteria. Not how it looks.

    Acceptance criteria say when a story is done, not how a control behaves at its edges. That gap belongs here. It only becomes a problem if nothing further down closes it.

  2. 2

    Design in Figma

    exists — their system

    States what it looks like — and carries the rule, typed into the component's own description field: what applies, the awkward cases, which spec it came from.

    Read back through the API, which makes it a channel rather than a note. Two variants can show both sides of a threshold; only the description says where it sits.

  3. 3

    Prose becomes a rule

    today by hand · skill planned

    Description and spec become one file: what applies, why, the edge cases, who decided — plus the executable logic. And a list of what none of them answered.

    Those get asked, never invented. An answer nobody chose is worse than an open question, because it looks like a decision.

  4. 4

    waitingroom

    built — this is it

    The rule becomes executable. A control panel drives it past its own thresholds, so what is on screen is the rule working — not one result somebody picked. Prototype, rule text and snippet all come from that one file.

    Explicitly not production code. That was the failure last time: something arrived looking like a delivery and got judged as one.

  5. 5

    Engineering checks it

    next step

    “Could you build this from it, without asking the designer?”

    Every “I'd still need…” is a line missing from the rule. That is the measurement; the prototype is only the means.

  6. 6

    Answers flow back

    built

    Answers become edge cases; changes become dated entries with a reason, not silent edits that pretend it was always so.

    Two of the three rules already carry a second entry — both found by working the prototype, not by reading it.

  7. 7

    Implementation

    their system

    Built in the real stack, from a rule with no gaps left. The snippet is framework-neutral on purpose: the decision, not the rendering.

  8. 8

    Storybook (the desk)

    exists — their system

    The desk a component is called to once its number comes up — the waiting list even has the column. This is where engineering already picks components up, and the rule's edge cases are the story list: one story per case, so what was a paragraph becomes a check that runs. The a11y addon turns “is this readable” into a test result rather than an opinion.

    Not a competitor to step 4, which is the obvious objection. The waitingroom runs the rule before the component exists; Storybook shows the component once it does. A rule that first appears here arrives after every decision it was supposed to inform.

Where the throughput comes from

  • Fewer questions back. An edge case settled in advance is a message not sent and a wait not had.
  • Fewer full rounds. Where component and design point at the same token, a colour change is a token change — nothing gets rebuilt or handed over.
  • Fewer decisions. Once “from five options on, a select” is settled, component forty inherits it. This is the one that compounds.

None of this makes anyone build faster. It removes the waiting in between.

Where this might connect to the regulatory side

A question for whoever owns that side, not a claim from here.

For medical devices, IEC 62366-1 wants usability handled as a documented process: a user interface specification has to exist, and use errors count as risks. An auditor reads the resulting file, not the product.

What that file asks of a decision is almost exactly the four fields a rule carries here — what applies, why, the awkward cases, who decided it when. Written down while building, they don't have to be reconstructed later from screenshots and memory.

The honest limits

  • Not every rule is safety-relevant. Radio group versus select almost certainly is not. A name that can be confused with another person's very much is — patient misidentification is a textbook hazard, and it is this same rule applied to a name column. Sorting which is which is the work.
  • Whether it applies at all depends on the product. Classification decides that, and not from the outside.
  • Gematik approval is a separate route. Which one is in force here — or both — is worth establishing before building a process around either.

Not “this satisfies the standard”. Rather: if the specification has to exist anyway, cheaper to have it fall out of the work than to write it twice.
