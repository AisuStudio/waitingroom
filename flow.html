The workflow

How a requirement becomes a component that can be built without asking back. Everything below is marked: what runs today, and what does not exist yet.

  1. 1

    Specification

    exists — their system

    States what is needed, as user stories and acceptance criteria — not how it looks. A spec that prescribes the control is reaching into design.

    Acceptance criteria say when a story is done. They do not say how the control behaves at its edges, and they are not meant to. So the behaviour is undefined here, and that is correct — it only becomes a problem if nothing further down defines it either.

  2. 2

    Design in Figma

    exists — their system

    States what it looks like. Components from the library, colour from the tokens.

    And this is where the rule is written down: in the component's own description field. What applies, what happens in the awkward cases, which spec it comes from. A few sentences, typed at the component by the person who decided it — no second tool, no second document to keep in step.

    The description is read back through the API, which is what makes it a channel rather than a note: everything downstream starts from the text the designer wrote, not from someone's reading of the screen.

    Figma itself holds states, not rules — two variants show both sides of a threshold but cannot say where it sits. The description is where that sentence goes, and it travels with the component when the component is reused.

  3. 3

    Prose becomes a rule

    today by hand · skill planned

    Description, spec and the cross-cutting rules become one file: what applies, why, the edge cases, who decided — plus the executable logic.

    And a list of what none of them answered. Those are asked, never invented. An answer nobody chose is worse than an open question, because it looks like a decision.

    The skill standardises the questions, not the answers. Every threshold gets asked what happens at exactly N; every space conflict, what may not be sacrificed.

  4. 4

    waitingroom

    built — this is it

    The rule becomes executable. A control panel drives it past its own thresholds — what is on screen is the rule working, not one result somebody picked.

    Prototype, rule text and snippet come from one file. Change the threshold and all three follow.

    Explicitly not production code. That was the failure last time: something arrived looking like a delivery and was judged as one.

  5. 5

    Engineering checks it

    next step

    “Could you build this from it, without asking the designer?”

    Every “no, I'd still need…” is a line missing from the rule. That is the measurement; the prototype is only the means.

  6. 6

    Answers flow back

    built

    Answers become edge cases. Changes become entries in the change trail, with a reason — not silent edits that pretend it was always so.

    Two of the three rules already carry a second entry. Both were found by working the prototype, not by reading it.

  7. 7

    Implementation

    their system

    Built in the real stack, from a rule with no gaps left. The snippet is framework-neutral on purpose: the decision, not the rendering.

Which artefact carries what

Each exists so something does not have to be decided twice. That, not typing speed, is where throughput comes from.

ArtefactCarriesStatus
rules/*.js
one file per rule
 The single source. Prototype, rule text and snippet all derive from it. built
Figma component description
at the component
 The designer's intent, without a change of tool. in use
design.md
one level above the rules
 What holds everywhere, so it is not repeated per component: names, selection controls, missing data. Plus the rule types and their questions. planned
rules skill
prose → rule
 Same questions, same format, every time. Translates — never authors. planned
check script
runs on every change
 All fields present, change trail and open questions non-empty, and no parameter spelled out as a literal in prose — the drift that already happened here once. planned
docs/*.md
generated
 The linkable, archivable form of a rule. Output, never source. built

In that order: the check script first, because it makes consistency measurable; design.md from what the script cannot check; the skill last, because it needs both as its yardstick.

Where the throughput comes from

  • Fewer questions back. Every edge case settled in advance is a message not sent and a wait not had.
  • Fewer full rounds. A colour change is a token change. Where component and design point at the same token, nothing is rebuilt and nothing is handed over.
  • Fewer decisions. Once “from five options on, a select” is settled, component forty inherits it. This is the one that compounds — and why a design.md of decisions beats one of style guidance.

None of this makes anyone build faster. It removes the waiting in between.

Where this might connect to the regulatory side

A question for whoever owns that side, not a claim from here. But the shape of the rule format was not chosen at random.

For medical devices, IEC 62366-1 asks that usability be worked on as a documented process rather than as taste. Two of its ideas matter here: a user interface specification has to exist, and use errors are treated as risks — a control that can be misread is a hazard, not a preference. Its results are collected in a usability engineering file, and an auditor reads that file rather than the product.

What such a file asks of a decision is almost exactly the four fields a rule carries here: what applies, why, what happens in the awkward cases, and who decided it when. Where those are written down as a by-product of building, they do not have to be reconstructed afterwards from screenshots and memory.

The honest limits

  • Not every rule is safety-relevant. The threshold between a radio group and a select almost certainly is not. A name that can be confused with another person's very much can be — patient misidentification is a textbook hazard, and it is the same rule, only applied to a name column. Sorting which is which is the work; claiming everything counts would be exactly the kind of over-documentation that makes people stop reading.
  • Whether it applies at all depends on the product. Classification decides that, and the answer is not obvious from the outside.
  • Gematik approval is a separate matter. Its requirements are not the same as the medical-device route, even though both end in someone checking documentation. Which one is in force here — or both — is worth establishing before anyone builds a process around either.

So: not “this satisfies the standard”. Rather — if a user interface specification has to exist anyway, it is cheaper to have it fall out of the work than to write it twice.
